# 通用调度策略

2026-10-16。中心按资源和运行环境调度，与H01等具体研究名称无关。任务包只提供程序、依赖、资源预算及可选数字规模；中心负责分配、监测和符合条件的恢复。

## 参考与取舍

- [Slurm 调度与回填](https://slurm.schedmd.com/sched_config.html)：按排队顺序保留启动机会，允许不会推迟前序任务的回填；预测必须区分历史估计与强制时间上限。
- [Kubernetes 多资源装箱](https://kubernetes.io/docs/concepts/scheduling-eviction/resource-bin-packing/)：分开过滤资源可行性与节点评分，减少资源碎片，保护稀缺容量。
- [AWS Batch 公平共享](https://docs.aws.amazon.com/us_en/batch/latest/userguide/fair-share-scheduling.html)：学习按用户共享资源的设计。当前不切固定用户配额，继续以排队顺序和大任务保留防止饥饿；有空闲时允许其他用户的兼容任务回填。未实现AWS的历史用量衰减算法。

## 中心当前算法

1. 在领取任务的数据库写事务内，主动更新未启动任务的内存预算，不依赖网页打开。完整运行峰值和数字规模匹配规则见《资源恢复策略附录》。运行中的执行限额不变，独立的调度预留可按下文完整记录学习。
2. 过滤离线、隔离环境、应用版本状态及单机容量。CPU、物理RAM、Windows提交额度、磁盘、许可席位、GPU和显存分别核算。单机即使清空仍放不下的提交额度或显存请求，不占该机的排队保留。
3. 按管理员设置的优先级从高到低，同级按原始入队顺序尝试启动。选择节点时最多观察后续32种不同资源形状，重复的小任务不会占满观察窗口。以CPU、RAM、提交额度、GPU占集群容量的最大比例衡量稀缺需求，降低一次放置损失的后续选择；结合已知耗时、GPU能力和负载评分。多卡机器优先分配满足条件的较小显存设备。
4. 暂时放不下的较早任务，在兼容池保留一个位置。未知结束时间时，后续任务仍可使用不增加该任务任何资源缺口的余量。已知结束上限时允许时间回填，计入最多30分钟环境准备、计算上限及2分钟收尾余量；也可证明后续任务继续运行仍不推迟前序任务。
5. 在执行租约写入前，最多检查512次候选搬移，将本轮尚未发出的一个任务换到其他节点，以容纳另一个等待任务。保留已接纳任务和前序保留；不移动已经发出的租约或运行进程。所有候选再次通过同一资源核算。
6. 整个分配计划原子写入，由各worker领取，避免轮询快的主机抢占所有任务。任务状态不因迟到的准备/运行采样回退。
7. 新Windows执行使用进程树提交内存硬限制，结合RAM轮询及主机压力准入。校正低估时，确认清理并保存输出后有界扩额重算。CPU线程不重叠分配，系统实际提交余量始终设准入门槛；调度预留与原执行上限分开核算。物理RAM重叠最多10%，必须满足新鲜、正常且可核验的观测条件。

## 验证和度量

可重复运行的离线基准为 `deploy/benchmark_scheduler.py`，不向平台提交任务。示例：

```text
python deploy/benchmark_scheduler.py --baseline /path/to/previous/scheduler.py --output /path/to/benchmark.json
```

基准覆盖4种异构节点、200组30任务队列、20组动态完成事件回放。后100组装箱输入使用独立种子。相同输入比较，旧版累计分配8635个CPU线程、380个GPU席位，新版8692和411；任务数量3180→3144，说明较大的计算获得更多容量，不能将任务个数等同吞吐量。事件回放平均完成时间722.05→708.10秒，模型CPU容量利用率57.17%→58.15%，GPU容量利用率56.88%→57.67%。有限批次含队尾排空阶段。这些是资源模型结果，不是机器实测占用率；算法是有界启发式，不保证每个输入的最优解。

首轮实机：普通账户上传8个1/2/4/8线程单元和依赖汇总，全部完成并下载校验。各单元验证继承的CPU亲和性与工作进程数；汇总验证前序结果、清理回执与内核限制。四机按逻辑CPU数加权的同时采样峰值48.71%，单机峰值分别36.40%、70.24%、59.49%、62.95%；不能把不同时间的单机峰值相加。

第二轮实机：普通账户上传14线程、16线程两个120秒计算及依赖汇总，均完成并下载校验。74个采样中，四机按逻辑CPU数量加权的同时采样峰值为66.8698%；不是不同时间单机峰值的平均，也不代表日常科研任务一直保持这一水平。两轮共12项执行全部成功，内核限制与清理回执均核验，按PID和创建时间远程检查无测试进程残留。上线前18项仍运行的任务保持原预算与CPU分配。

359项测试通过。中心最终部署备份为 product-center-20261016-211122；scheduler.py、server.py远端SHA256与本地一致。准备包备份 submission-materials-20261016-211327。证据位于受保护目录 `.private/scheduler-generic-20261016/` 和 `.private/scheduler-saturation-20261016/`，最终证据为前者的 completion-proof.json 与 release-verification.json。

Win1当前受系统提交额度约束，Win3当前受工作盘剩余空间与运行任务磁盘预算约束；Win2/Win4压力测试时已分配满各自19个可调度线程。按用户允许不强求70%的标准结束本轮压测，保留这些独立资源约束。CPU达到70%还依赖可运行任务数量、程序并行度及各资源是否满足，不能用测试负载表示日常科研任务已达到该水平。

## 2026-10-17 通用学习与管理员优先级

调度器不按科研名称、当前队列ID或用户名称选择任务。它接受统一的资源请求、依赖、运行环境和优先级；不同应用共用过滤、排序、保留、回填和多资源装箱规则。旧任务包的程序适配器只提取数字规模，不决定派发资格。

预留学习同样支持任意应用：使用提交规范中的 `resources.workload.family/features` 数字规模，按同用户、同程序指纹、同运行环境版本的完整成功记录计算规模峰值上包络；不超过已验证规模的两倍外推。缺少数字规模时，仅在完全相同的不可变提交包与单元上学习，不跨不同输入猜测用量。运行预留要求至少三个完整成功、确认清理的样本，加1.6倍系数、0.75GiB余量及可核验的保留开销，并不低于当前运行历史峰值保护值。新鲜用量、SYSTEM进程身份、系统提交状态、正常压力观察缺一不可；触限重试、固定预算或禁止重跑仍保留原预留。调度请求是预测，不改正在运行的硬限制、CPU分配或输入；未知程序不享有旧流式程序的特殊缓冲假设。

lab 管理员可对批次的待启动单元或单个排队/暂停单元设置优先级。界面提供低(-10)、普通(0)、高(10)、紧急(20)，接口接受-100至100整数。数字越高越先；同级按入队时间，自动恢复沿用最初入队时间，人工重新提交则重新入队。依赖、资源和隔离条件仍须满足，优先级不抢占已租约或运行任务。暂停/继续及后续重试保留该单元的优先级。批次修改返回实际影响单元和明确回执；当前无待启动单元返回409。记录管理员、原值、新值及影响任务，普通账户不能调用调整接口。

管理员在任务页、运维页及明细可见提交者账户名、原始上传时间和优先级；原始上传时间按提交批次最早记录保存展示，不因重试变成重试时间。普通账户继续只看到自己的任务。队列卡片按优先级和入队顺序展示，但是否可启动仍由资源和依赖决定。

状态页面使用协商gzip及单一在途刷新，避免较大任务历史在公网反复积压；此传输优化不参与资源估计或派发优先级。

## 2026-10-17 缺失规模维度的输入绑定预留

完整规模字段仍使用至少三项完整成功并确认清理的记录。对于中心已核验缓冲及保留数组增长边界的程序，若旧清单缺少规模维度，不能把缺值当零，也不能仅凭当前低RSS缩额。中心将缺失维度绑定到真实不可变ZIP的SHA256及输入组身份；只有相同包、相同输入组、相同已知规模、相同程序族、用户及运行时的完整成功记录才能作为参考。代码已核验的随时长增长保留量另计。一个这样的完整参考即可建立临时预留，但采用峰值×2+1GiB的较大余量，向上取0.25GiB，并继续受当前进程树历史峰值×1.6+0.75GiB的下限保护。

该证据路径在通用resource_policy学习器中处理；旧包适配器只提供输入绑定和增长边界证据，不按任务ID、用户或队列特判。缺少完整参考、输入不同、无增长边界证明、旧观测、系统压力、固定预算、禁止重跑或触限重试均不能使用此路径。当前执行限额、PID、CPU亲和性、输入和工作盘不改，临时预留只参与新任务准入；CPU及系统提交额度继续单独严格核算。对于尚未启动且有相同输入绑定的任务，也使用同一个完整记录包络校正，不只对新上传任务生效。

## 2026-10-17 未来资源保留与扩额恢复

当前派发仍可使用已验证的学习预留及最多10%的RAM弹性额度；这些观测随时可能失效，不能当作未来一定可用的容量。计算前序任务的有界释放时间、判断后续回填是否会推迟前序任务时，剩余执行按原执行预算核算，不使用临时学习预留或弹性额度。该预测不写回任何运行任务；每次实际领取仍重新检查实时资源。

已经因内存触限而扩额重试的单元，不再用旧的同输入成功记录缩回预算；规模学习和同输入校正均遵守这一限制。未来正常的新单元仍可学习完整成功记录。没有可比的完整记录时，当前低占用不能证明整个任务峰值低；不同COMSOL模型也不能仅凭同批次关系互相替代内存预算。

## 2026-10-17 代码分配结构与完整执行数据的资源校正

新增通用非负仿射上包络：按同用户、同运行环境及已核验的分配结构收集完整成功且清理确认的RSS/私有提交峰值。拟合计入固定开销，截距上移以覆盖全部训练峰值，再以1.6倍和0.75GiB余量、向上0.25GiB取整；逐规模留出验证不通过时不采用。未知程序继续原有保守模型。识别条件是完整程序束SHA256及结构化规模，不含任务ID、用户名、主机或队列特例。

旧流式程序适配器现在从实际输入NPZ数组头读取顶点数，从输入读细胞/连接数，并用中心完整结果及原程序哈希补齐缺失的实际分段数。常驻状态、缓冲与随时长增长的保留数据分维度核算，不再在完整峰值之上重复叠加粗略时长开销。模型拟合利用不同规模、不同已完成时长的数据；长任务至少需要三个不同规模的完整同等或更长时长记录覆盖。相同不可变包/输入组的完整短执行可作为常驻状态基线，只增加经完整数据拟合的非负保留量增幅；输入不同不能借用该基线。未绑定基线的各规模维度不超过已覆盖最大值4倍；原通用workload比例包络仍保持2倍限制。任何实际运行峰值×1.6+0.75GiB继续作为临时预留下限。

串行固定工作区适配器逐个核对几何NPZ、冻结完整细胞报告的源哈希、顶点和分段数据；依据原代码的等待式子进程调用、固定记录长度、替换式状态及数组，计算各子单元工作区的最大值，不把串行数量误当并发数。未知版本、缺失字段、源绑定差异、固定预算、禁止恢复或触限重试均不适用。调度器和拟合器不执行用户提供的估算代码。

早期已运行任务若缺失内核内存限制，SYSTEM任务LabCompute-MemoryGuard只操作该runner原有、独占且覆盖完整进程树的JobObject，把原提交预算加原标准0.25GiB监督余量应用到内核；不重新归属进程、不改PID、CPU亲和性、预算数值或kill-on-close清理权。目标句柄只在核验和配置期间复制，随后关闭。节点当前租约认证回传原限额、PID/创建时间，必须与新鲜SYSTEM进程身份观察一致；证据失效即取消进一步借用，不停止运行任务。没有完整核验不接受旧任务缩额。实机覆盖已有嵌套venv子进程，确认PID/创建时间和原清理机制保持。

估算任务启动时可共享自身已加的安全余量：必须具有内核限制、可从头恢复、非触限重试，并且同机全部既有预留已有完整来源/代码证据及正常新鲜压力观察。借用不超过该新任务的估算填充量，且现有与新启动信用合计不超过派发后RAM请求的10%和整机RAM的10%；当前物理可用内存扣系统保留、CPU ID和OS提交额度仍严格核算。只记录实际所需借用，任务原执行预算不变。未来回填释放预测继续禁用这些临时信用。


## 2026-10-17 调度审查修复

结果上传与执行清理分开确认：未收到本租约的清理确认或有效清理回执时，finish返回409，任务继续占用原资源；独立存储观察器只在原监督进程已退出后，核验原PID及创建时间或独立Broker退役回执，再由原Worker继续回传；原JobObject与独立账户Broker保留唯一清理权，观察器不按任务可写的PID记录发出终止信号。缺失或不完整的进程证据不作为清理成功。

通用比例学习不再同比缩小完整峰值中的固定工作区；未经结构验证的模型只允许大于等于1的规模系数。程序束指纹补入原生扩展、共享库、Java/脚本、版本化so及无扩展名程序；当前排队任务恢复到校正前预算后，使用实际包重建程序族并重新学习，触限扩额重试不缩回。运行执行的spec、输入、CPU亲和性和硬限额保持。

时间回填给本次租约设置绝对占用期限，复用现有Worker节点时钟转换与runner暂停检查；暂停不延长该期限。新尝试清除旧期限，再由本次放置决定。人工重试的排队起点与自动失败次数分开，自动恢复保留其来源起点；历史队列仅按中心审计证据补齐，原上传时间不变。

磁盘不再重复预留已占用部分：独立、低优先级后台扫描各任务实际分配字节（Windows压缩/稀疏文件按物理分配计量），随后采集卷空闲量；预留剩余增长量。可信、完整且未过期的观测才可抵扣，未知/过期按完整预算回退。目录扫描不阻塞进程身份和卷观测。过期独立进度回退到本租约的新Worker进度。

程序/结果解析移至SQLite领取写事务之外，按不可变提交包、任务spec和完成记录构建模型快照；锁内只读取匹配快照和实时资源，并原子写入租约。缺失快照保守回退，下一轮刷新。模型拟合缓存按完整输入隔离并返回独立副本，不缓存实时准入结果。

卷/进程观测与旧账户ACL清理也分别执行，慢清理不会阻塞资源采样；采集进程使用现有监督记录，逐一核验PID与创建时间，避免重复遍历全机进程。

观测JSON统一读取时尽早关闭文件句柄，再解析内容；Windows请求共享删除权限，但不把共享标志当作持有句柄期间一定能替换文件的保证。新监督进程对usage/process_tree的临时写锁继续下一采样，旧监督进程不热修改；原文件锁故障按既有有界策略恢复。
