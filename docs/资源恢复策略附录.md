# 资源恢复策略附录

### 内存申报只加一层余量（2026-10-20）

- `resources.memory_basis="peak"`：未含安全余量的整个进程树峰值；这是 `estimated` 默认口径。中心只在首次形成预算时加 `×1.3+0.5 GiB`，向上取0.25 GiB。
- `resources.memory_basis="budget"`：申报数字已含安全余量，中心不再加初始余量；仍可使用 `estimated` 的历史学习。`fixed` 默认且仅支持此口径。
- 不要将中心显示的执行限额再次作为 `peak` 上传。反复解析同一声明不会重复加余量；中心保留原申报、口径、系数和首次预算。历史学习结果替换预算，不与首次余量累加。
- 有完全相同输入的完整运行记录时，校正值为峰值的1.5倍（不再叠加固定GiB或二次取整余量）；运行硬限额保持不变。跨规模预测的不确定性另行记录，不能冒充完全可比实测。
- 随包用简短 `MEMORY_ESTIMATE.md` 记录原始峰值、同时存活的数据/工作区、参考执行ID与是否完整、未确定项，以及数字是否已经含余量。不需要额外试跑；此说明不作为科学验收或计算准入门槛。
- 缺少某个规模字段时，不能用未测量的固定“每对象规模”占位值冒充已知规模；必须标注未知和临时预算，不套用旧任务的大额预算下限。提交内存单独估计实际私有分配，不再无依据套用 RAM×1.2+2。
- 平台只核算资源与执行，不安排科学复核，不要求为估计内存额外计算，不自动重新提交已有任务。

例如：预计RAM峰值2 GiB、私有提交峰值2.5 GiB，使用 `peak` 后首次预算为3.25/3.75 GiB；若申报的是已经含余量的3.25/3.75 GiB，则明确用 `budget`，最终仍是3.25/3.75 GiB。

### 科研集群申报方式与中心的预留/上限

科研集群一般由用户在提交脚本中声明资源。例如Slurm：

```bash
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=8
#SBATCH --mem=12G
#SBATCH --time=12:00:00
```

这里 `--mem=12G` 表示每节点内存；`--mem-per-cpu=2G` 表示每个所分配CPU的内存，两者不要同时使用，也不要误把总内存再乘线程数。CPU并行度应与程序实际可用并行度相符。

申报依据依次是：相同程序/输入规模/并行方式/运行环境的完整历史用量；程序的同时存活数据和库/求解器工作区；软件官方规模说明；没有这些依据时明确标注临时估计。集群使用jobstats、sacct等历史记录修正后续申报；MaxRSS的进程/作业步统计口径不一定等于全进程树总峰值，不能盲目求和或直接照搬。中心不为收集样本额外试跑或重算。

- **原始申报**：agent提供的峰值或已含余量预算，通过memory_basis区分。
- **调度预留（request）**：排队及节点准入扣除的额度；有完整可比记录后按峰值纠偏，任务结束后释放。它不是提前分配好的物理内存页。
- **执行上限（limit）**：执行停止线，与调度预留独立展示。已有运行任务的上限不改；上限比预留大不表示差额已得到保障，压力出现时停止新增派发，不靠重算运行任务腾空间。
- **实际用量**：进程树当前用量与累计峰值；未结束只能叫累计峰值。

中心的一份完整同输入、同用户和运行时记录即可用于纠偏，不要求为了预算完成第二次计算。完整同输入的峰值采用最多1.5倍策略，不与旧申报或初始余量累加；这不是Slurm行业统一倍数。明确不完整的采样峰值、失败/触限前峰值、缺少原生完整退出证据的旧记录不能用于缩减预留。旧Windows记录须有原生退出0、清理完成、有效进程树峰值，以及完整运行的开始/结束时间和时长回执（或有效内核记账），才作为完整运行的观测记录；这仍是观测峰值，不是未采样时刻的数学上界。

Slurm资源申报与本中心JSON格式不同，不要把sbatch脚本当成本中心入口。继续使用准备包计算器和随包估算依据要求。

参考：[Slurm内存申报](https://slurm.schedmd.com/cons_tres.html)、[Harvard集群资源与历史用量说明](https://docs.rc.fas.harvard.edu/kb/faq/)。

## 弹性调度补充（2026-10-16）

CPU 核心、物理内存和系统提交额度分别核算。尚未启动的 estimated + from_start 任务根据完整成功记录和任务规模校正；不再统一缩减15%。fixed、never、已扩额重试以及运行中任务不缩额。没有可比记录时保留申报预算。

物理内存承诺允许最多 10% 的轻度重叠，只计入运行至少 60 秒、采样在 20 秒内、未扩额重试的 estimated/from_start 任务。需要正常且核验的压力观测、可靠的系统提交额度，并且没有外部共享计算。额度同时受主机总 RAM 的 10% 限制，不借用当前空闲量中的系统预留。CPU 和系统提交额度均不超配。观测过期或出现压力时撤回新增超配额度，停止不符合预算的新派发；运行任务保留各自限额。峰值同时出现仍可能换页。

同一组重叠兼容主机只为最早的大任务保留一个启动位置，其他主机继续回填，避免多个大任务把整个兼容池全部占位。 未知结束时间时，回填不增加前序任务在CPU、RAM、提交额度、磁盘、许可或GPU上的缺口；按时间回填时包含最多30分钟环境准备和2分钟收尾。租约发出前可重新安排本轮未启动任务的位置，已经发出的租约不搬移。

面向需要了解中心策略的维护者；提交任务无需实现这些算法。默认值可由管理员配置调整。

`estimated` 模式中，memory_gb/commit_gb 是预计峰值。中心分别按 `ceil((估计×1.3+0.5)×4)/4` 形成初始预算，提交预算不低于 RAM 预算。`fixed` 模式直接使用申报值作为预算和限额。小任务应按需求填写，避免只因省略字段而采用较大的默认预算。

- **内存低估**：estimated + from_start，计算阶段明确触及 RAM/提交限额，确认进程清理且原结果保存后，中心自动增加预算并创建新执行。普通预算的触限维度至少翻倍；完整记录校正后的预算按观测及至少1.5倍触限维度扩额，避免直接恢复虚高申报。覆盖观测峰值余量；默认最多2次，自动恢复预算上限默认 RAM64/commit128 GiB。保留原输出，同一逻辑单元显示最新执行。
- **环境准备与隔离启动失败**：确认清理后，符合恢复分类的任务默认最多重新准备2次。运行中断仅在 from_start 且确认清理后自动重启；与准备恢复共用执行重试计数。
- **预算偏高**：同一用户、完全相同 ZIP 与单元、相同运行时修订，一次完整成功并确认清理后，可用最高峰×1.5（最小请求0.25 GiB），不叠加固定余量，下降超过25%才应用。同程序和运行时、相同 workload.family 与规模字段的完整成功记录，可按最大规模比投影峰值，取所有可比记录的保守上包络；只允许最多2倍外推，缩小比例最低0.25，再按峰值×1.6+0.75 GiB、向上取0.25 GiB、至少1 GiB，下降至少15%才应用。预算不超过原申报形成的初始预算。旧H01任务由固定代码读取包内已知规模字段；未知类型不猜测。
- **系统级限制**：Windows Job Object 对整个执行进程树设置提交内存硬上限，创建子进程前核验。计算阶段为提交预算加0.25 GiB监督进程余量；准备阶段至少2 GiB再加余量。系统级提交额度限制与轮询RAM限制并行。已经运行的旧执行保持原机制；新执行与自动恢复执行使用硬限制。系统峰值计数可能包含被拒绝的申请，不能把它当作实际驻留内存；中心保存此证据用于有上限的扩额恢复。

- **结果回传**：传输、打包或校验失败保留输出并退避重试，不重新计算。确认执行停止后释放计算资源，结果保存成功后出现下载入口。
- **取消**：停止等待或执行，自动清理进程，已有输出继续交付。不会自动重启已取消任务。


## 缓冲计算预算与多工作盘（2026-10-17）

运行时间不是所有程序的内存规模。对已提交的固定 H01 程序，中心代码确认电流按1ms缓冲写盘、向量逐缓冲重置，并核验事件数量上界后，以细胞数、记录段数和缓冲窗口匹配完整成功记录；另为随总时长增长的参考信号、滤波和事件数据增加保守内存余量。不同输入条件只在程序、运行时和状态维度相同的情况下共享包络。未识别的程序仍采用声明的数字规模，不因短任务占用低就下调长任务。

当前队列同步采用该校正；已运行任务不缩额、不搬盘、不改变CPU亲和性。校正后仍保留系统硬限制和有上限的扩额恢复。平台故障重试保留原逻辑单元的排队年龄。

工作盘按卷分别核算容量与已有承诺，优先使用原工作盘，容量不足时选择管理员配置的D/E盘。盘符由平台选择；任务保持原规范的工作路径。新增目录服务在派发前完成目录和连接准备，失败会重新选盘；已有目录与结果不迁移。C盘保留至少10GiB或5%，其他工作卷保留至少4GiB或2%，取较大值。

跨盘任务的专属账号只获本任务物理目录的权限。执行结束后自动删除临时账号并移除目录授权；权限清理由数字SID处理，避免账号已删除导致名称解析失败。已核验的中心任务不会因跨盘路径被重复计为外部负载。

准备阶段下载采用临时文件、长度与ZIP完整性检查后替换。兼容尚未重载的旧worker：目录服务仅对中心记录“尚未计算、提交包ZIP损坏”的失败检查本机启动证据；确认无runner、无启动标记、无broker请求后，中心按最多两次的准备恢复策略重新派发。原结果与失败记录保留；运行后的任务检查失败不进入此通道。

运行中的任务可以使用中心学习出的调度预留：只有程序、规模和完整成功记录可核验时才启用，并持续检查运行峰值、系统余量及资源压力。其执行硬限制不变，释放的是后续任务准入时的历史过量预留；缺少证据则继续保留原预算。当前排队任务与新任务使用相同调度规则，用户无需试跑或校准。

### 不完整规模的严格输入绑定（2026-10-17）

已核验缓冲及保留内存增长边界的程序，缺失维度可由整个不可变提交包SHA256及输入组身份锁定。不同包或输入组不合并，不猜测缺失维度。运行临时预留允许使用一个同输入、同已知规模、同程序/用户/运行时的完整成功清理记录，按历史峰值×2+1GiB及目标任务保留开销计算；无这种证据仍要求原来的三项可比完整记录。所有实时压力、身份、提交余量及历史峰值保护保持。该分支只改变准入预留，不改变运行执行限额。
