## 1. 任务包结构

一个 ZIP 对应一个批次，包含 1–200 个计算单元。根目录直接放 `manifest.json`，不要再套一层总文件夹。

```text
manifest.json
main.py
requirements.txt
inputs/data.csv
```

推荐声明资源估计；下例适用于可安全从头重复执行的 Python 任务：

```json
{
  "schema_version": 1,
  "name": "数据分析批次",
  "tasks": [
    {
      "id": "analysis",
      "name": "数据分析",
      "kind": "python",
      "runtime": "python",
      "entry": "main.py",
      "args": ["--input", "inputs/data.csv"],
      "requirements": "requirements.txt",
      "restart_policy": "from_start",
      "resources": {
        "mode": "estimated",
        "cpus": 2,
        "memory_gb": 2,
        "commit_gb": 3,
        "disk_gb": 4,
        "wall_minutes": 120
      }
    }
  ]
}
```

无额外依赖时，可以去掉 requirements 字段和文件。`from_start` 表示在全新工作目录重跑不会产生不可接受的外部副作用；否则填写 `never`。

**务必显式选择恢复策略：省略 `resources.mode` 和 `restart_policy` 时，实际为 `fixed + never`，不会启用内存低估后的自动扩额重算。** 可安全从头重跑的任务使用上例的 `estimated + from_start`；有外部副作用的任务应保持 `never`。

ZIP 上传上限默认 2 GiB；解压上限 8 GiB，最多 20,000 个条目。`manifest.json` 和每份依赖文件各不超过 1 MiB。路径用 `/` 分隔；不允许绝对路径、`.`/`..` 路径段、反斜杠、Windows 保留文件名、符号链接、加密 ZIP 或大小写冲突的重名文件。

## 2. 清单字段

顶层字段为 `schema_version`（固定为 1）、`name`（可选批次名）、`tasks`（计算单元数组）。每个单元支持：

| 字段 | 含义与默认值 |
| --- | --- |
| `id` | 批次内唯一 ID，1–80 个字母、数字、`_` 或 `-`；省略时依次为 `task-1`、`task-2`。有依赖时建议明确填写。 |
| `name` | 展示名称，默认入口文件名去扩展名；名称最多保留 120 字符。 |
| `kind` | `python`、`matlab`、`comsol`；默认 `python`。 |
| `runtime` | 中心已发布的环境 ID，默认与 kind 相同。 |
| `entry` | 必填，包内入口相对路径。对应 `.py`、`.m`、`.mph`。 |
| `args` | Python 参数字符串数组，最多100项，每项最多2048字符；MATLAB/COMSOL 参数写进脚本或模型。 |
| `requirements` | Python 依赖文件相对路径；省略时，若根目录有 requirements.txt 就自动使用。填 `null` 可明确不使用该文件。 |
| `depends_on` | 同批次前序 ID 数组，默认空；不能重复、不存在或构成循环。 |
| `restart_policy` | `never`（默认）或 `from_start`。 |
| `resources` | 下表中的结构化资源字段。 |
| `platforms` | 可选的 Windows/Linux 执行适配表；新任务应对所有可运行平台提供入口、runtime 与依赖。没有声明的平台不被猜测兼容。COMSOL 适配必须填写模型所需 `min_version`。 |

CPU、内存等请写在 `resources` 内。顶层旧字段 `cores`、`memory_gb`、`estimated_minutes`、`max_minutes`、`target` 不参与 ZIP 任务的资源和主机分配。中心自动选主机，用户身份由登录账户绑定。自然语言估算说明不作为机器执行指令。

## 3. 资源估计

| resources 字段 | 范围与默认值 |
| --- | --- |
| `memory_basis` | `peak`（未含余量）或 `budget`（已含余量）；estimated 默认 peak，fixed 默认且仅支持 budget。 |
| `mode` | `estimated` 或 `fixed`；省略为 `fixed`。建议新任务明确使用 `estimated`。 |
| `cpus` | 1–256 的整数，单位为逻辑 CPU；Python 默认1，其他类型默认4。 |
| `memory_gb` | 0.25–1024 GiB；Python 默认4，其他类型默认8。 |
| `commit_gb` | 不小于 memory_gb，不超过4096 GiB；省略等于 memory_gb。 |
| `disk_gb` | 1–16384 GiB，默认4；中心实际取申报值与“包解压大小×2+2 GiB”的较大值。 |
| `gpus` | 0–16 的整数，默认0。 |
| `gpu_memory_gb` | 每张所申请 GPU 需要的可用显存，0–256 GiB，默认0。申请显存时同时设置 gpus。 |
| `wall_minutes` | 兼容旧包的可选元数据（旧上传器接受1–10080分钟）；不再作为科学计算的强制终止时长。可省略，科学计算不限时。 |

估计整个计算进程树的峰值：输入载入、计算临时副本、并行工作进程、结果整理都要计入。已有相同输入规模的实测可用作参考，无需为了提交额外试跑。 对分块或流式计算，按同时存活的最大数据块、缓冲窗口和并发副本估算，再加必须保留到结束的数组、事件和结果整理空间；总处理量或总时长不应直接当作全部常驻内存。

- **CPU**：申报代码能够实际利用的并行度。多进程或线程数读取 `LAB_COMPUTE_THREADS`，不要固定占满整台主机。
- **RAM**：估计同时驻留的内存，不把整机容量当作任务需要。
- **提交内存**：估计进程树需要操作系统提供后备存储的私有内存峰值；不机械取 RAM 的两倍。协议要求申报值不低于 RAM。
- **磁盘**：覆盖输入、前序结果、临时文件及输出，并留打包空间。平台自动选择有容量的工作盘，无需指定盘符；使用任务工作目录内的相对路径。本字段用于调度与部分容量检查，不是完整磁盘配额隔离。
- **时间**：填写覆盖最慢正常计算阶段的上限；这是停止线，不是预计完成时间。准备环境单独限30分钟。入口运行后动态补装依赖的时间计入计算时间。

`estimated` 的值是预计峰值，中心自动增加初始余量；`fixed` 直接作为预算和限额。小任务按实际需求填写。具体预算公式见准备材料中的《资源恢复策略附录》。

### 内存申报只加一层余量（2026-10-20）

- `resources.memory_basis="peak"`：未含安全余量的整个进程树峰值；这是 `estimated` 默认口径。中心只在首次形成预算时加 `×1.3+0.5 GiB`，向上取0.25 GiB。
- `resources.memory_basis="budget"`：申报数字已含安全余量，中心不再加初始余量；仍可使用 `estimated` 的历史学习。`fixed` 默认且仅支持此口径。
- 不要将中心显示的执行限额再次作为 `peak` 上传。反复解析同一声明不会重复加余量；中心保留原申报、口径、系数和首次预算。历史学习结果替换预算，不与首次余量累加。
- 有完全相同输入的完整运行记录时，校正值为峰值的1.5倍（不再叠加固定GiB或二次取整余量）；运行硬限额保持不变。跨规模预测的不确定性另行记录，不能冒充完全可比实测。
- 随包用简短 `MEMORY_ESTIMATE.md` 记录原始峰值、同时存活的数据/工作区、参考执行ID与是否完整、未确定项，以及数字是否已经含余量。不需要额外试跑；此说明不作为科学验收或计算准入门槛。
- 缺少某个规模字段时，不能用未测量的固定“每对象规模”占位值冒充已知规模；必须标注未知和临时预算，不套用旧任务的大额预算下限。提交内存单独估计实际私有分配，不再无依据套用 RAM×1.2+2。
- 平台只核算资源与执行，不安排科学复核，不要求为估计内存额外计算，不自动重新提交已有任务。

例如：预计RAM峰值2 GiB、私有提交峰值2.5 GiB，使用 `peak` 后首次预算为3.25/3.75 GiB；若申报的是已经含余量的3.25/3.75 GiB，则明确用 `budget`，最终仍是3.25/3.75 GiB。

准备包内 `tools/estimate_memory.py` 是通用静态预算计算器，使用方法见 `tools/内存预算工具.md`；agent负责填写实际分配与未知项，工具不启动计算，也不会再加安全系数。

### 科研集群申报方式与中心的预留/上限

科研集群一般由用户在提交脚本中声明资源。例如Slurm：

```bash
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=8
#SBATCH --mem=12G
#SBATCH --time=12:00:00
```

这里 `--mem=12G` 表示每节点内存；`--mem-per-cpu=2G` 表示每个所分配CPU的内存，两者不要同时使用，也不要误把总内存再乘线程数。CPU并行度应与程序实际可用并行度相符。

申报依据依次是：相同程序/输入规模/并行方式/运行环境的完整历史用量；程序的同时存活数据和库/求解器工作区；软件官方规模说明；没有这些依据时明确标注临时估计。集群使用jobstats、sacct等历史记录修正后续申报；MaxRSS的进程/作业步统计口径不一定等于全进程树总峰值，不能盲目求和或直接照搬。中心不为收集样本额外试跑或重算。

- **原始申报**：agent提供的峰值或已含余量预算，通过memory_basis区分。
- **调度预留（request）**：排队及节点准入扣除的额度；有完整可比记录后按峰值纠偏，任务结束后释放。它不是提前分配好的物理内存页。
- **执行上限（limit）**：执行停止线，与调度预留独立展示。已有运行任务的上限不改；上限比预留大不表示差额已得到保障，压力出现时停止新增派发，不靠重算运行任务腾空间。
- **实际用量**：进程树当前用量与累计峰值；未结束只能叫累计峰值。

中心的一份完整同输入、同用户和运行时记录即可用于纠偏，不要求为了预算完成第二次计算。完整同输入的峰值采用最多1.5倍策略，不与旧申报或初始余量累加；这不是Slurm行业统一倍数。明确不完整的采样峰值、失败/触限前峰值、缺少原生完整退出证据的旧记录不能用于缩减预留。旧Windows记录须有原生退出0、清理完成、有效进程树峰值，以及完整运行的开始/结束时间和时长回执（或有效内核记账），才作为完整运行的观测记录；这仍是观测峰值，不是未采样时刻的数学上界。

Slurm资源申报与本中心JSON格式不同，不要把sbatch脚本当成本中心入口。继续使用准备包计算器和随包估算依据要求。

参考：[Slurm内存申报](https://slurm.schedmd.com/cons_tres.html)、[Harvard集群资源与历史用量说明](https://docs.rc.fas.harvard.edu/kb/faq/)。

### Agent 打包前必须完成的内存预算步骤

这是提交者agent的准备职责，不能只把工具复制进包里就算完成：

1. 在生成最终manifest之前，主动阅读 `tools/内存预算工具.md`，为每个独立计算单元准备预算输入表；相同程序和分配规模可共用一份表，但须列出适用的任务ID。不能因为都是同一批次就共用一个数字。
2. 按实际代码的同时存活分配填写解释器/原生库、输入、缓冲、私有进程副本、原生求解器工作区、结果整理与打包阶段；注明各项来自代码尺寸、文档、经验还是完整可比执行。无法量化的项必须填入 `unquantified`，禁止删除未知项来取得“完整”状态。
3. **实际运行** `python tools/estimate_memory.py resource-estimates/<任务ID>/memory-estimate.json --output resource-estimates/<任务ID>/memory-budget.json`。这只是静态资源算术，不是运行仿真。若使用已有完整可比执行的峰值覆盖静态结果，必须在估算说明中列出执行ID、程序/规模/环境的可比依据及覆盖的内存范围；仍保留静态输出，不伪装为工具自动推断。
4. 将最终采用的数字写入manifest，明确 `memory_basis`。工具输出不含安全系数，应使用 `estimated + peak`；若agent另行采用已含余量的预算，只能用 `budget`，并记录从工具结果到最终数字的每一项增加。禁止重复叠加平台余量。
5. **最终ZIP必须随包保留** `resource-estimates/<任务ID>/memory-estimate.json`、`memory-budget.json` 和 `MEMORY_ESTIMATE.md`。估算说明须包含最终RAM/提交预算、采用的口径、原始依据、阶段与并行假设、所有未知项、工具命令和日期；可使用准备包的模板。交付时简述这些文件的位置，并明确是临时估计还是有完整可比实测支撑，不能声称“工具已保证准确”。

未知项不触发额外试跑或科学复核。无法量化的原生工作区仍可按明确说明的临时预算提交，不能因此暗中取消任务；中心不新增科学验收或估算文档自动阻塞门。已经冻结、排队或运行的包不为补这份说明而重新提交。

### 提交者 agent 如何静态估计内存

提交者提供任务包、数字预算和简短资源估算依据，无需额外试跑或校准。按各阶段同时存活的数据计算峰值，再取整个进程树的最大值：

- 数组按元素数×数据类型字节数计算，并计入同时存在的输入、副本、输出和解压缓冲。稠密矩阵按行数×列数，稀疏矩阵按实际非零项及索引存储计算。
- 多进程的私有数据按同时运行的工作进程数计入；共享只读数据计一次。线程不会天然把全部内存乘以线程数。
- 神经仿真计入分段、突触、状态变量和记录缓冲。只有确实保留全部时间序列时，记录内存才随时长增长；流式写盘按缓冲大小计算。
- 加入解释器、依赖库及必要工作区。不要使用压缩包大小或整机容量代替预算；estimated 已由中心加余量，避免重复放大。

例如100万行、64列的 float64 数组约0.477 GiB，若同时保留输入及两个同尺寸副本，总计约1.43 GiB，再加约0.5 GiB运行开销，RAM估计约2 GiB。提交内存另按私有分配估计，以下2.5 GiB仅为示例。

可在 resources 中增加机器可读的规模信息：

```json
{"mode":"estimated","cpus":1,"memory_gb":2,"commit_gb":2.5,"workload":{"family":"dense-transform-f64-v1","features":{"live_elements":192000000}}}
```

workload.family 使用1–80位字母、数字、下划线、点、冒号或短横线；features 为1–8个非负有限数字计数，键名为1–40位字母、数字或下划线。规模应表达实际内存增长量，例如矩阵元素数而非只有边长；同一 family 保持相同定义。中心还绑定程序、运行时和用户身份，只利用可比的完整运行记录；超过已有规模两倍的任务不会依靠该模型下调。无法提供可靠规模时可省略 workload，中心保留较保守的申报预算。

中心每12小时对比实际调度预留与进程树内存峰值。具备完整可比计算记录的预留，以完整峰值和当前累计峰值中较大者的1.5倍为上限；启动初期的低用量不能作为最终峰值。运行中的硬限额不因该巡检下调。缺少完整峰值依据时标为待确认。内存溢出或超过内存限额的解决建议必须包含提高对应的 memory_gb 或 commit_gb 预算；调整预算不等于允许重复提交。

### COMSOL 等求解任务的内存估计

不要把结果文件或模型文件的磁盘大小直接当成内存需求，也不要把单个求解进程的内存机械乘以 CPU 线程数、累计时间步数或循环阶段数。应估计同时存活的求解器工作区、保留解、前阶段初始化解、结果导出副本和子进程；如果每阶段会清理旧解，只计同时保留的部分，确实累计保留的解则必须计入。

优先采用相同任务、输入规模和运行环境的完整进程树峰值。求解器自身显示的内存、瞬时低用量、首个计算块和失败前峰值都不能冒充完整运行峰值。没有完整可比记录时，明确标注“临时估计，待完整运行记录”，说明估计依据；不要照搬其他模型的大额预算。已有失败记录可作为局部资源线索，但必须核对它覆盖到哪个执行阶段。

`estimated` 模式由平台自动增加初始余量，提交者不要再重复叠加同一层安全系数。执行限额与调度预留分开记录；完整执行后，以全程实测峰值校正后续估计，有完整可比记录的预留遵守1.5倍上限。若触发内存或提交内存限额，反馈必须包含提高对应预算，并保留原输出；不得为取得样本而擅自重复提交或重算。

中心依据进度和历史耗时估算完成时间。科学计算不限墙钟时长；旧 wall_minutes 不提供强制资源释放保证。新调度器仅按实际资源余量回填，旧驻留版本待安全切换；申报资源不等于主机已经具备相应能力。

## 4. GPU 任务

使用 `runtime: "python-gpu"`：Windows x64、Python 3.11、PyTorch 2.7.1 + CUDA 12.6。四种显卡为 RTX 3050（8 GiB）、RTX 4060（8 GiB）、GTX 1660（6 GiB）、RTX 3090（24 GiB）。实际可用显存扣除桌面占用，以中心采样为准。

可直接从准备材料中的 `GPU示例.zip` 开始。包根目录的 manifest.json：

```json
{"schema_version":1,"name":"GPU矩阵计算","tasks":[{"id":"matrix","kind":"python","runtime":"python-gpu","entry":"main.py","restart_policy":"from_start","resources":{"mode":"estimated","cpus":2,"memory_gb":1.5,"commit_gb":2,"disk_gb":4,"gpus":1,"gpu_memory_gb":1,"wall_minutes":10}}]}
```

main.py：

```python
import json
from pathlib import Path
import torch

x = torch.arange(4096, dtype=torch.float32, device="cuda").reshape(64, 64) / 4096
y = x @ x.T
torch.cuda.synchronize()
Path("outputs").mkdir(exist_ok=True)
Path("outputs/result.json").write_text(json.dumps({"sum": y.sum().item(), "gpu": torch.cuda.get_device_name(0)}))
```

示例预算只适用于上面的小型矩阵计算；训练模型或更大数据须重新估计峰值。

此环境自动安装固定的 torch 和 numpy，无需在 requirements.txt 重复声明。需要 torchvision 或 torchaudio 时，可在依赖文件中写包名，或由入口直接导入触发自动安装；中心将版本约束为 CUDA 12.6 对应的 torchvision 0.22.1、torchaudio 2.7.1。与模板冲突的版本要求会被拒绝，不会静默换成 CPU 版本。

中心先使用缓存，缓存缺包时联网补装；每个任务仍有独立环境。执行前再次验证 CUDA 可用并完成微型计算。中心另为 GPU 环境预留 8 GiB 安装空间，任务的 disk_gb 只需覆盖自己的输入、临时文件与输出。

当前已发布 GPU 调度的 Windows 主机各为单卡；A800 Linux支持1–8卡单机任务，使用 python-gpu-linux；跨主机联合训练尚未支持。独立 GPU 计算可拆成多个单元，由平台并行安排。

中心任务间整卡分配，代码读取 CUDA_VISIBLE_DEVICES 后使用逻辑设备编号，不硬编码物理卡号。GPU 与 Windows 桌面显示共享，准入检查当前利用率、已识别的外部计算进程和可用显存，并保留 0.5 GiB 显存余量。该机制不是恶意代码的设备访问硬隔离，平台面向课题组可信用户。

显存申报是准入要求，不是硬限额；GPU OOM 不触发 RAM 扩额，已有输出仍会交付。驱动、系统 CUDA 编译工具链、商业许可证由中心维护，任务安装不会修改它们。预编译的 PyTorch CUDA 运算不要求用户安装 CUDA Toolkit；自定义 CUDA 扩展、其他框架或未发布的系统依赖须由中心提供对应环境。仅声明 GPU 数量不会把 CPU 程序改成 GPU 计算。

## 5. 运行环境与依赖

入口不得把其他历史任务工作目录中的安装包、解释器或软件目录当作持久运行环境。软件依赖使用中心登记的共享运行时或随包材料；前序计算结果通过任务依赖声明领取到本任务独立目录。存量跨任务路径依赖在登记并迁移前保留原路径，维护时不因任务已结束或已有ZIP就清理对应运行环境。

准备材料中的 `运行环境快照.json` 可离线阅读，无需账户；其中同一 ID 的多种 status 表示不同主机的安装情况。`version` 是该环境报告的软件版本，专用环境不一定指 Python 版本。最新信息以登录后的 `/api/environments` 返回为准；环境按主机列出。 中心后台每分钟检查环境目录变化，自动同步独立快照、agent 准备包内快照及 README 日期；只在环境内容变化时更新，单纯在线状态波动不会重复打包。选择 kind 匹配且 status=ready 的环境，实际启动还取决于主机在线、开放派发和可用资源。

常用环境包括 `python`（基础 Python）、`python-science`（科学计算包）、已发布的专用 Python 环境，以及 MATLAB/COMSOL。具体版本和软件包取环境目录，不把某个节点的软件安装状态硬编码到任务包。

Python 每次执行使用独立虚拟环境：安装环境模板，再安装本单元 requirements，再执行 pip check。依赖建议固定版本；同包不同单元可各自指定依赖文件。

```text
humanize==4.13.0
```

不要假设其他任务安装过的包会出现在自己的环境。中心可使用管理员维护的 wheelhouse；普通用户任务的私有 pip 缓存会在交付后清理，不保证跨任务共享下载缓存。不要打包整套虚拟环境。

`vendor/` 直接加入 Python 导入搜索路径，适合纯 Python 源码，例如 `vendor/myhelpers/__init__.py` 对应 `import myhelpers`。中心不会扫描并安装 vendor 中的 wheel 文件。

随包离线 wheel 放入 `wheels/`，并在 requirements.txt 中逐行填写包根目录相对路径，例如 `./wheels/your_package-1.0.0-py3-none-any.whl`（替换为真实文件名）。pip 的工作目录是任务包根目录，即使 requirements 位于子目录也一样。二进制 wheel 必须匹配所选节点的操作系统、架构与目标 Python（Windows x64 或 Linux x86_64）；仅随包携带一个 wheel 不代表它的所有传递依赖都已包含。

任务入口直接导入缺失的顶层 Python 包时，中心可按已知映射或同名包自动补装，单次执行最多尝试24个不同包。完整依赖仍应写在 requirements 中，尤其是分发包名与导入名不同、版本约束或子进程需要的依赖。自动补装不等于任意第三方库内部或子进程缺失依赖都能识别。

二进制库需与所选环境的操作系统、架构和 Python 版本兼容。CUDA、系统程序、MATLAB 工具箱和商业许可证使用管理员发布的环境。

## 6. 多任务与依赖

管理员设置的最高正优先级具有资源等待屏障：现有执行继续完成；只要该级仍有等待资源的单元，较低优先级不领取新任务，释放的资源优先积累给最高级。最高级任务全部实际领取资源后，剩余资源再分配给低级任务；候选规划显示可放置不会提前放行低级任务。排队的必要前序在本轮规划中继承其后序的高优先级，原始优先级不改写。资源、依赖与安全准入仍须满足；明确暂停的任务不参与屏障。所有任务均为普通优先级时保留原有排队和有界回填规则。

将同一实验批次的独立计算放入 tasks，平台自动并行；需要前序输出时明确写 depends_on。例如：

```json
{
  "schema_version":1,
  "name":"两阶段计算",
  "tasks":[
    {"id":"solve","entry":"solve.py","restart_policy":"from_start","resources":{"mode":"estimated","cpus":1,"memory_gb":1,"commit_gb":1.5,"disk_gb":4,"wall_minutes":30}},
    {"id":"aggregate","entry":"aggregate.py","depends_on":["solve"],"restart_policy":"from_start","resources":{"mode":"estimated","cpus":1,"memory_gb":0.5,"commit_gb":1,"disk_gb":8,"wall_minutes":10}}
  ]
}
```

每个单元有独立工作目录，不共享写入。后序在前序成功且结果到达中心后启动，读取 `dependencies/solve/work/outputs/…`；只注入显式声明的直接前序。dependencies/ 由中心管理，有依赖的包中不得自带该目录。

后序磁盘预算需覆盖整个前序结果包的解压内容并留至少1 GiB余量。当前前序结果解包仍采用8 GiB/20,000条目的检查上限；若前序输出过大，应在提交设计时按独立数据单元拆分。

前序自动恢复期间后序等待；恢复成功后自动放行。前序最终失败后，未执行的后序明确结束，不无限等待。

## 7. 程序、进度和输出

工作目录为任务包解压根目录，输入输出均使用相对路径。入口位于子目录时，工作目录仍是包根目录。建议将主要结果写入 outputs/。

程序无需键盘或窗口交互，成功返回退出码0，失败返回非零。入口退出前等待自己启动的全部计算子进程结束。Python 使用入口脚本；MATLAB 使用 -batch；COMSOL 使用 batch，模型输出为 computed_model.mph。

可在工作目录根部原子更新 progress.json：

```json
{"completed":25,"total":100}
```

completed、total 是有限数值，要求 `0 ≤ completed ≤ total` 且 total>0；文件最多4096字节。以样本、参数组等实际工作单位更新，先写临时文件再替换。未提供进度也可运行，中心在有足够数据时给出预计时间。

进度应对应用户的实际目标量，例如处理样本数、训练轮次、参数组合数或累计循环次数。默认表示整体进度；阶段内的百分比明确标记 `scope: "stage"`，不要把求解器阶段比例当成整个任务的完成比例。可以同时报告阶段名称、单位及多个目标：

```json
{"completed":8000000,"total":10000000,"unit":"次循环","stage":"自适应演化","scope":"overall","metrics":[{"name":"已处理参数组","completed":3,"total":8,"unit":"组"}]}
```

没有整体计数时可只上报 `{"stage":"整理结果"}`；只有阶段计数时使用 `{"completed":3,"total":10,"scope":"stage","stage":"当前训练轮","unit":"批"}`。最多8个metrics，每项包含name、completed、total及可选unit；各目标分别显示，不把不同单位相加。

Python、MATLAB及其他可输出文本的程序，也可逐行输出 `LAB_PROGRESS ` 加同一JSON对象，及时刷新标准输出。Python示例：`print('LAB_PROGRESS '+json.dumps({'completed':25,'total':100,'unit':'样本'}),flush=True)`。复杂项目建议持续写根目录progress.json，以保留最新进度。上传规范不要求提交者额外试跑或校准。

中心自动读取COMSOL本次执行的comsol_batch.log，显示求解阶段及阶段比例；累计循环等业务目标由任务按上述格式报告。参考文件和前次运行的进度不作为当前进度。没有可靠整体比例时，平台显示“计算中”、当前阶段和已运行时间，不显示虚假的0%；阶段比例不用于推算整个任务的完成时间。多单元批次分别显示已完成、运行及等待数量，并展示运行单元的进度。

结果 ZIP 包含 work/ 下的输出及执行日志、资源统计和环境记录。多单元批次可整体或分别下载。批次打包只包含页面当前计算单元各自最新一次执行已经生成的结果；最新执行仍排队或运行且尚无结果时，不用旧失败输出填补。历史执行的已有输出保留在对应执行记录中单独下载。中心完成表示计算成功退出且结果保存，不附加科学验收动作。

## 8. 自动恢复与交付

- **内存低估**：`estimated + from_start` 的计算触及 RAM/提交限额后，中心在保存输出、确认清理后增加预算并重算；超过恢复上限会结束并提供已有输出。
- **环境准备或运行中断**：中心对可恢复故障自动重试；运行中断重算要求 `from_start`。
- **预算偏高**：中心根据完整成功运行的峰值、相同程序与运行环境，以及数字化任务规模调整尚未启动的 estimated + from_start 任务；当前排队任务同样适用。没有可比的完整记录时保留申报预算，不再统一下调15%。运行中的限额不缩小，不要求用户试跑或校准。校正后触限会根据观测扩额并自动重算。
- **结果回传**：自动重试交付，不重新计算；保存成功后出现下载入口。
- **取消**：停止等待或执行、清理进程并保留已有输出，不自动重启。

每次重试从新目录开始，不猜测检查点格式、不混用失败执行的输出。任务错误、超时和 GPU 显存不足不触发 RAM 自动扩额。中心自动清理临时环境、缓存和任务进程，保留输入、结果与执行记录。

## 9. 交付与自动上传

提交者静态核对入口路径、输入、依赖、任务 ID/依赖关系、资源字段及输出位置后交付 ZIP，说明批次名称和结果位置即可。

交付可上传 ZIP 并给出文件链接后，提交者 agent 必须主动询问用户：“可上传包已提供，是否需要我实时跟进任务运行？如果需要，希望每隔多久检查一次，例如每30分钟、每2小时，或你指定的间隔？”不要为了等待答复而延迟交付文件。

跟进为可选服务，不要求提交者持续在线。用户同意后，按其确认的间隔跟进排队、实际计算进度、运行错误、结果保存和下载状态；未确认是否跟进或间隔时，不自行创建定时监控。用户明确选择无需跟进时，完成交付即可。跟进不包含任何科学复核，也不授予重新提交或重算的权限。

如已获用户授权自动上传，可使用 submit_batch.py 或 POST /api/jobs（multipart 文件字段 package）。浏览器/API 写入均使用登录会话及 CSRF；上传使用稳定的 Idempotency-Key。相同账户、相同文件的网络重试复用同一标识；有意重新计算用新标识。不同文件复用旧标识会拒绝。

上传回执返回任务 ids 与 batch_id。普通批次可用回执 batch_id 调用批次下载/取消；页面状态可能给出兼容的展示 ID，两者均受账户权限检查。凭据留在受保护的客户端配置中，不放入任务 ZIP。

当前运行开放状态以平台页面为准；主机维护、旧任务交接与部署记录见平台运维交接，不属于用户任务包协议。


Linux 外部任务由中心主机主动 SSH 派发并收回结果，提交者电脑离开校园网不影响执行。运行状态通过原生退出、进程身份、运行日志和结果保存交付确认。Linux 内存记录若仅为采样峰值，会标记不完整，不作为完整峰值下调预留；内存限额触发的建议包含提高 memory_gb 或 commit_gb 预算。

### 调度和分配

CPU池4–255（252个逻辑线程）按任务分配互不重叠的亲和性；0–3留给系统。整机RAM保留64 GiB，调度同时扣除现有占用、运行任务预留及提交预算系统余量。取消旧8线程/16 GiB/单并发限制，任务可并发，最多252个一线程单元。单任务RAM仍受清单1024 GiB上限约束，多任务可使用整机剩余内存。工作盘覆盖 /Dataset0–5 与 /CodeStorage，优先 /Dataset2；逐盘按实时空闲量减64 GiB及已预留空间分配，空间不足的盘暂停新派发，恢复空间后自动参与。每项任务固定一个工作盘，不把多盘零散空间相加承诺给单任务，最长10080分钟。8张GPU按卡独占分配，已有外部GPU进程占用的卡暂不派发。GPU任务读取CUDA_VISIBLE_DEVICES绑定；此为设备可见性约定，不是恶意代码的内核级GPU隔离或显存硬限额。

派发前同时检查操作系统、已发布运行时、后端硬限制、依赖、全平台最高优先级屏障和当前资源。超出后端能力会显示原因并留在队列，不先领取后失败。最高优先级仍采用现有全平台规则：只要该级有排队任务，低优先级不补位；即使A800暂时空闲，也不会绕过该屏障。候选放置不等于实际领取。

上限针对中心最终展开的执行预算；`estimated`会增加初始余量，不能将估计值误当作最终执行限额。固定预算示例：

```json
{
  "schema_version": 1,
  "name": "Linux CPU计算",
  "tasks": [{
    "id": "compute", "name": "计算", "os": "linux",
    "kind": "python", "runtime": "python-science-linux",
    "entry": "main.py", "restart_policy": "never",
    "resources": {"mode": "fixed", "cpus": 4, "memory_gb": 4,
      "commit_gb": 6, "disk_gb": 4, "wall_minutes": 120}
  }]
}
```

GPU单元填写 `"os":"linux"`、`"runtime":"python-gpu-linux"` 及 `resources.gpus`（1–8）、每卡 `gpu_memory_gb`。程序仅使用分配后的逻辑GPU编号0至gpus−1；多卡训练需程序自行启动进程/分布式后端，申请多卡不等于代码自动并行。CPU任务不会获得GPU设备。

程序遵守 `LAB_COMPUTE_THREADS` 及已设置的 OMP/BLAS线程上限，不使用整机256线程自动建池。输入、临时文件、依赖安装和输出仅写本任务目录；临时空间受工作盘预算约束。没有图形桌面、交互sudo、系统软件安装或访问其他任务目录的承诺。额外 Python 依赖通过任务内 `requirements.txt` 安装，目前只支持PyPI可用的二进制wheel，不修改已发布基础环境。

Linux RAM限额由cgroup MemoryMax执行（含计入cgroup的页缓存），禁用任务swap；`commit_gb`仍为调度预算，不等同Windows私有提交量的独立内核限制。磁盘采用用量监测与超额停止，不是文件系统硬配额。当前Linux峰值为采样记录，不作为完整可比峰值下调预留。内存触限时反馈包含提高对应memory_gb或commit_gb预算；是否重算由授权和重启策略决定，禁止重复提交。

## 跨平台任务发布与并发（2026-10-23）

Agent 打包新任务时，应优先提供 Linux 与 Windows 适配，共享同一份科学输入；平台差异只放在入口、运行时与依赖文件中。Python 用 pathlib/相对路径，遵循 LAB_COMPUTE_THREADS；外部进程按当前系统选择已发布可执行程序。NEURON .mod 随源码与对应平台构建入口，不能把 Windows DLL 用于 Linux。COMSOL 使用相对文件引用并声明模型的最低应用版本。平台适配不改变资源预算、科学条件、输入身份或依赖关系。

示例（根目录仍提供默认入口）：

```json
{
  "schema_version": 1,
  "tasks": [{
    "id": "electrode",
    "kind": "comsol",
    "entry": "models/electrode.mph",
    "runtime": "comsol-linux",
    "os": "linux",
    "platforms": {
      "linux": {"runtime": "comsol-linux", "min_version": "6.4"},
      "windows": {"runtime": "comsol", "min_version": "6.4"}
    },
    "restart_policy": "never",
    "resources": {"mode":"fixed", "cpus":2, "memory_gb":4, "commit_gb":4, "disk_gb":4, "wall_minutes":120}
  }]
}
```

Python 的 platforms 可分别声明 entry、runtime、args、requirements（null表示无依赖）；依赖文件必须随包提供。每个平台只允许 entry/runtime/args/requirements/min_version，禁止借适配表覆盖资源、用户身份或任务类型。中心在唯一租约形成前选定适配；已经运行的任务不改变入口或迁移。若程序依赖特定系统、GPU、尚未安装的软件或只有单平台的二进制，Agent 必须明确列出缺失适配，不能伪称所有平台可用。MATLAB 尚未发布的节点不会运行 MATLAB 任务；COMSOL 6.4 模型不会下派到仅有6.2的节点。

不设置“每机只能一项”或其他任意 COMSOL 项数限制。中心按独立 CPU 集、RAM/提交预算、工作盘及实际可用许可证尽可能并发，Dell 优先、A800 次之；不足时使用其他满足应用版本及隔离要求的节点。传包/准备中、已派发和实际求解分别展示，不能把分配资源当作已启动求解。同一不可变任务包按批次、文件长度及修改版本在节点缓存一次，各任务使用独立副本；缓存不采用网络文件哈希，不跨输入版本复用，不对任务做科学二次复核。


## 节点原始错误自动反馈

节点 runner 自动采集原始退出码、应用错误及其上下文，不经过 AI 改写。已确认清理且节点报告失败后，中心自动在任务反馈中保留一份去重原始回执；可在任务状态详情查看并下载原始错误 JSON，无须用户先提交反馈。`GET /api/jobs/<job_id>/feedback` 的 `native_error` 为结构化对象，含 `native_exit_code`、`exit_code`、`detail`、`evidence[].source/message/context` 和结果下载地址，仅任务所有者及管理员可读。兼容切换期间也可读取 `feedback` 中 `request_id=system:native-exit-v1` 条目的 `reply` JSON。错误报告是执行证据，不包含科学结论或 AI 推断。

包装脚本若把子程序日志重定向到独立文件，可在本次生成的 `execution-result.json` 中声明 `"error_logs":[{"path":"native_batch.log","kind":"comsol"}]`，kind 可取 python/comsol/matlab；path 必须为本任务 work 内的相对路径。节点只将指定原生日志中的明确错误和有界上下文写入回执；中心不读取这些日志做二次分析。用户输入包不得预置 execution-result.json。

## Linux隔离GPU编号与恢复输入（2026-10-24）

中心spec.gpu_ids记录宿主分配，隔离任务内只暴露已分配设备，CUDA_VISIBLE_DEVICES使用从0开始的局部编号。提交入口使用任务内CUDA设备，不将宿主编号回写覆盖；非隔离任务由启动器保留宿主编号。两类节点使用同一规则。恢复入口从原始不可变任务包获取原始配置，不能把已被前一次脚本改写的work输入当成初始输入；每次准备可能再修改配置时，恢复前须重新按登记出处还原，保留已有完成输出与失败历史。

## 执行回执与续传版本（2026-10-24）

节点已有 exit.json 不能覆盖仍然存活的操作系统进程；只有原生执行单元和进程树清理确认后，才能释放计算资源或发布完成回执。结果整理与下载不触发重算。
